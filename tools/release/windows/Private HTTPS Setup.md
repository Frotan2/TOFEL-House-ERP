# Set up private staff HTTPS

The institute Windows and network administrators perform this once on the production PC, after authorization to install and qualify the delivery. Start with the ERP running locally in **REFUSED** mode. Verify the private network and HTTPS before the Owner prepares the activation request; verify staff workflows only after approved activation.

## Verify the files and create the configuration

1. Before opening the installer, compare its SHA-256 with the value in the separately trusted release record. Use an institute-approved graphical SHA-256 tool. Also verify the installed `caddy-windows-amd64.zip` beside this guide. Its pinned SHA-256 is `ad93112d335ee687100c4c9f11bced16ca590377976b7fe7883882b9e797e472`. Stop if either comparison fails or you cannot verify it. File Explorer does not provide a general file SHA-256 check. Use the institute's existing software authorization policy.
2. In the institute's router and private DNS consoles, reserve the server's private IPv4 address and point one private DNS name to it. Confirm the address appears on one active adapter on the server. Identify the single approved staff IPv4 network and prefix (it can be on a routed private subnet). Leave guest networks and the internet unable to reach the server, and leave port forwarding disabled.
3. Open **Private HTTPS** in the ERP launcher or open **Private HTTPS Setup.cmd** beside this guide. Enter the exact DNS name, server IPv4 address, and approved staff network and prefix. Select **Prepare proxy files** and choose a local NTFS folder. The form checks the bundled archive against its pinned checksum, extracts only Caddy, preserves the Windows download restriction, and saves the generated configuration with it in a new folder. **Save new Caddyfile** is available for an administrator managing an existing proxy. The configuration binds Caddy to the selected address, limits staff source addresses, and sends requests to ERP at `127.0.0.1:8000`.

## Set up the proxy and firewall

1. The administrator places the prepared `caddy.exe` and `Caddyfile` in `C:\ProgramData\TOEFL House ERP\Private HTTPS` and creates a `certificates` subfolder there. In **Properties > Security > Advanced**, allow only administrators and SYSTEM to manage the program and configuration. Give one dedicated standard Windows account read and execute access to those files and **Modify** only in the `certificates` subfolder. Prevent unrelated accounts from accessing that subfolder or replacing the files or their parent directory.
2. In **Windows Defender Firewall with Advanced Security > Inbound Rules > New Rule**, choose **Custom**. Select only the installed `caddy.exe`. Choose **TCP**, set **Local port** to **Specific Ports: 443**, and leave remote ports unrestricted. In **Scope**, set **Local IP addresses** to just the reserved server IPv4 and **Remote IP addresses** to just the approved staff subnet. Select **Allow the connection** and only the institute-managed **Domain** or **Private** profile in use; leave **Public** unchecked. Review overlapping rules for the executable and port 443. Keep direct access to ERP ports 8000 and 9000 closed. [Microsoft firewall guidance](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure)
3. Where institute policy permits a persistent scheduled process, open **Task Scheduler > Create Task** and name it **TOEFL House ERP Private HTTPS**. In **General**, choose the dedicated standard account, select **Run whether user is logged on or not**, and leave **Run with highest privileges** unchecked. The administrator handles any required batch-logon right using institute policy. In **Triggers**, add **At startup**. In **Actions**, add **Start a program** with these fields:
   - **Program/script:** Browse to `C:\ProgramData\TOEFL House ERP\Private HTTPS\caddy.exe`.
   - **Add arguments:** `run --config "C:\ProgramData\TOEFL House ERP\Private HTTPS\Caddyfile" --adapter caddyfile`
   - **Start in:** `C:\ProgramData\TOEFL House ERP\Private HTTPS`
4. In **Settings**, allow the task to run on demand, enable restart on failure, clear the execution time limit, and choose **Do not start a new instance**. Save it and choose **Run**. If the institute requires a Windows service instead, use its approved service installation procedure. The ZIP does not supply a graphical service installer, and the Windows Services console does not create a service from this executable. Keep the same limited identity, paths, and firewall restrictions. [Windows startup tasks](https://learn.microsoft.com/en-us/windows/win32/taskschd/starting-an-executable-on-system-boot) · [Caddy runtime and service options](https://caddyserver.com/docs/running#windows)

## Verify network access before activation

1. After Caddy starts, the administrator selects **Export public CA certificate** in the private HTTPS form. The form saves only the public certificate as a new `.cer` and shows its SHA-256. If the operator cannot read the protected CA folder, have the authorized administrator perform the export. Issue the SHA-256 through a trusted channel separate from the certificate transfer and check it before importing. Root trust applies beyond the ERP hostname, so distribute it only to authorized managed devices under institute policy. If policy permits a per-user import, open **Manage user certificates > Trusted Root Certification Authorities > Certificates > All Tasks > Import** for the designated user and select the verified `.cer` file. [Caddy local HTTPS](https://caddyserver.com/docs/automatic-https#local-https) · [Microsoft managed certificate distribution](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/distribute-certificates-group-policy)
2. On two authorized staff devices, open `https://` followed by the approved DNS name. The browser must show the exact name and trusted HTTPS with no warning, and receive an ERP response. An operational refusal is expected at this stage. Do not enter staff credentials or enable workflows yet.
3. From a guest or otherwise excluded network, try the reserved server IPv4 directly on HTTPS; it must not connect. A certificate warning or page from the server counts as a failed isolation check. From a staff device, confirm there is no direct connection to the server on ports 8000 and 9000. After an approved restart, confirm Caddy starts without a Windows sign-in and the HTTPS checks still pass once the ERP is running. If the ERP requires the authorized operator to open **Start** after boot, record that step in the institute's startup procedure.
4. Record the exact URL and results. The Owner can proceed to **Activation Request** once these network checks and the other required qualification checks pass. Keep the ERP in **REFUSED** mode until its signed approvals are applied.

## Verify staff workflows after activation

Once the qualified installation is legitimately activated, create a separate ERP login for each staff member and assign their approved role and branch access. Sign in on two authorized devices with different staff accounts and use synthetic records to confirm an allowed operation, denial of a restricted role or branch, and that a live update reaches the other authorized device. Hold the staff handover if any check fails.

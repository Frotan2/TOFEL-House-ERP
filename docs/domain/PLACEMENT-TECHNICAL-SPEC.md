# Placement — bounded technical specification

Date: 2026-09-14 · Source baseline: `63e00b2737b7bc3f70553a68ca6aee2141474af8`

**Design selected for implementation-authorization review; no implementation performed or authorized.** F01–F05 are CLOSED/APPROVED in [PLACEMENT-APPROVED-BASELINE.md](PLACEMENT-APPROVED-BASELINE.md). This document and [PLACEMENT-TECHNICAL-READINESS.md](PLACEMENT-TECHNICAL-READINESS.md) are the authoritative technical gate. They refine the earlier blanket requirement for P1–P5 before implementation: missing institutional values may remain unset during an authorized synthetic-data build, with affected real operations disabled. They are not invented defaults or reopened business decisions. Production remains **REJECT**.

## 1. Scope and selected implementation decisions

One owned extension app, **`toefl_house`**, installed after the existing `foundation_security` app; depend on native Frappe/ERPNext/Education and compose supported hooks. No upstream/core patch, separate identity provider, replacement ledger, new service, frontend framework, dependency upgrade or foundation change. MariaDB is authoritative; native Redis/queues are dispatch facilities, not score/state authorities. Use native Desk for authorized administration and same-origin Frappe-served candidate pages/commands; no separate public service or remote-assessment launch.

Bounded scope: verified native subject references; managed bank and safe staging import; fixed blueprints and constrained form allocation; six skills; objective/manual scoring; supervised digital, physical and hybrid sessions; optional audio; review/release; history, restricted reporting and retention controls. Vocabulary/language knowledge and grammar remain separately attributable even in a combined section.

Excluded: Student/Customer conversion; admission/enrollment/academic-result writes; finance/payroll; curriculum creation; adaptive/IRT scoring; AI grading; remote proctoring/conferencing integration; offline synchronization; public signup; routine video/biometrics; official/mock TOEFL or CEFR outputs; live pilot/deployment. Native catalog references may support a recommendation but never register a learner. Digital live speaking uses an assessor-observed session and recorded ratings; embedded conferencing is not necessary or selected.

## 2. Native identity and access ownership

- Native **Lead** when Program/year is unknown, native **Student Applicant** when meaningful, existing **Student** for a verified returning learner. A case has exactly one original typed subject reference. Preserve it after conversion/relinking; authorized corrections create dated link-history events, not a new person master or destructive merge.
- Introduce a narrowly scoped **Subject Access** record: native User, typed native subject, purpose, verification event, validity/revocation and verifying staff reference. It owns entitlement/provenance, not name/contact/Student truth. One active candidate entitlement per User; conflicting claims fail closed. Conversion is outside this slice.
- Digital candidate uses a verified **native Website User** with only placement-candidate privileges and no Desk, Student, Guardian, admissions or staff role union. A returning person's conflicting staff/student login is not widened; a separately verified candidate account may link to the same existing subject without changing `Student.user`. Legitimate distinct account/contact arrangements are owner configuration; no fake emails, generic shared accounts or staff credentials. Physical assessment remains available under its approved identity procedure.
- Candidate has no generic CRUD/list permission on bank, keys, policy, native Lead/Applicant/Student or full attempt/evidence records. Candidate commands return minimal delivery/result projections after active subject/attempt checks. Placement does not expose native person documents as a portal shortcut.
- Staff roles: content author, content/policy approver, invigilator, assessor, reviewer/releaser, identity administrator and records administrator. Organizational owners approve assignment/delegation; role union never cancels state, assignment or conflict checks. Institution/site is tenant; branch scopes restrict work but do not replace site isolation.

## 3. Logical records, keys and integrity boundaries

Use owned DocTypes with explicit logical states, rather than native cancel/amend semantics that could delete history. No generic custom person, class or result master. Physical field/index migrations will be delivered only after authorization.

| Aggregate | Fields/references and required uniqueness |
|---|---|
| **Item / Stimulus Revision** | Stable family ID + immutable revision; controlled skill/level/difficulty/topic/type/mode tags, prompt/media, rights and status. Unique `(family, revision)`; stimulus dependencies and enemy/near-duplicate families explicit. |
| **Key / Rubric Revision** | Separate restricted parent; item/task revision, bounded marking definition or criterion descriptors/anchors. No secrets in child rows of a readable prompt. Unique definition revision; no arbitrary Python/JS/regex evaluation from content. |
| **Blueprint / Policy Revision** | Blueprint owns quotas, timing, navigation, compatible modes and pool rules; policy owns criteria aggregation, actual course mappings, retake/release/retention parameters. Draft → Reviewed → Published → Retired; publication freezes meaning. |
| **Case / Subject Access / Assignment** | Original native subject, purpose, active decision reference; access verification/revocation; actor role and component/review scope with effective interval. Case lock serializes attempt creation and decision changes. |
| **Attempt / Component Session** | Case, ordinal, pinned blueprint/policy, expected revision, mode, assignment, approved accommodation, server clock segments, state. Unique `(case, ordinal)` and `(attempt, component, session revision)`; one live session per component. |
| **Form Manifest** | Exactly one allocation per attempt; selected revisions/stimulus groups, occurrence IDs, candidate-specific order/permutations, marks/time profile, selection algorithm version and protected randomness provenance. Never regenerate on refresh. |
| **Response / Evidence** | `(attempt, occurrence, revision)`; append-only acknowledgements and current pointer until seal. Evidence binds private File/chunk manifest or physical script/custody references, permitted purpose, uploader, capture/receipt times and seal. |
| **Score / Rating / Review** | Objective score keyed by sealed response manifest + key/scorer version; rating keyed by assignment + criterion + revision; independent moderation/adjudication references. Supersede, never overwrite submitted findings. |
| **Decision / Incident / Appeal** | Case/attempt/evidence/policy/course references; rationale, validity, review/release actors and supersession/revocation; explicit incident remedies and appeals. One effective decision pointer per case/purpose. |
| **Operation / Exposure** | Durable operation key, input hash, actor/scope, state, outputs and dispatch intent. Unique `(site-local operation kind, idempotency key)`; exposure event unique `(attempt, family, event kind)`. Ledger retains reservations, deliveries/printing and approved reclaim reasons. |

Parent-owned child rows suit blueprint quotas and non-sensitive rubric criteria; separately permissioned evidence, keys, ratings and review must remain separate parents. Add unique constraints and query indexes for the listed keys, active assignments, subject links, published eligible pools, operation state and retention due dates. No reliance on Frappe `modified` alone for concurrency or user-supplied status fields.

## 4. Command boundary and transitions

All candidate commands require native session/CSRF protection; no guest or arbitrary-method proxy. Inputs are scoped IDs, expected revision, bounded response payload and stable idempotency key. Server derives actor, policy, deadline, key, score and authority. Use a server-created, request-local command context inaccessible through serialized document fields; never trust `flags`, `ignore_permissions`, actor, approved state or score supplied by the client.

| Command family | Preconditions → effect |
|---|---|
| Author/import/review/publish | Scoped author edits Draft only; staging validation, duplicate/rights checks and independent content approval precede publication. Imports cannot publish or amend approved content. |
| Register/allocate | Verified subject, published compatible blueprint/policy and permission → new attempt plus one immutable allocation; no native student/enrollment side effect. |
| Verify/start/deliver | Approved mode/accommodation, supervised verification and assignment → clock start and allowed component payload; delivery/exposure recorded before prompt/packet leaves the server. |
| Save response / upload / seal | Own active component, current revision, valid occurrence/type and timing → acknowledged revision; submit or timeout locks accepted evidence, including explicit missing items. |
| Mark / rate / moderate | Sealed inputs and current authorized worker/assessor; restricted keys; conflict checks → versioned score/rating. Review never edits the original response. |
| Resolve incident / reassess | Recorded incident, delegated authority and compatible evidence → audited resume/replacement/void action; new allocation for replacement, no hidden reroll or best-section merge. |
| Release / supersede / revoke | Complete valid evidence, required moderation and independent approver → immutable released decision plus atomic case pointer. A newer incomplete/invalid attempt does not displace an earlier valid release. |
| Appeal / retain / dispose | Current scope, approved deadline/exception or records authority → linked review/hold/disposal operation; no routine destructive business delete. |

Attempt states: Registered → Allocated → Verified → In Progress → Sealed → Marking → Review → Finalized. Incident Hold may interrupt the path; No Show/Voided/Invalid are distinct terminal outcomes. Decision states: Draft → Reviewed → Approved → Released → Superseded/Revoked. "Finalized" is not "released". Missing config/identity/media/moderation yields an explicit hold, not zero, automatic failure or guessed recommendation.

## 5. Allocation and exposure algorithm

Select **bounded constrained backtracking over indexed, stratified eligible pools**, not an adaptive model or unrestricted random draw. Candidate difficulty/level categories are editorial inputs; quotas do not prove psychometric equivalence.

1. Resolve immutable blueprint and subject exposure history. Remove unpublished/quarantined/rights-expired, mode-incompatible, previously excluded family/stimulus, enemy and exhausted entries.
2. Select whole stimulus/task groups and compatible standalone occurrences against skill/category, marks, time and difficulty constraints. Stable option IDs permit answer-preserving permutations; do not shuffle order-dependent content. Prefer low-exposure eligible families using server-generated cryptographic randomness within constraints.
3. Lock a blueprint/pool revision allocation guard, then exposure rows in canonical order; recheck eligibility/caps and reserve exposure before committing the attempt/manifest. This intentionally serializes a pool's allocation initially for correctness. Upgrade to finer locks only after measured contention, not by weakening constraints.
4. Initial engineering guardrails: at most 10,000 solver expansion states or two seconds of solver wall time, whichever occurs first; at most three whole-command transient/deadlock retries. Database lock waits must also be bounded and tested; limits are engineering tuning, not an owner policy or SLA. On infeasibility/budget exhaustion return "allocation unavailable" with an operator reason. No silent quota/exposure relaxation. Persist only a completed manifest; a retry with the same operation returns it, never a new form.
5. Delivery/printing converts reservation to irreversible exposure before response bytes/packet are issued. Lost network acknowledgement may overcount exposure conservatively. Reclaim only demonstrably undelivered expired reservations. Printed/abandoned tasks remain exposed; new item IDs do not reset family history.

Published config specifies reuse windows/caps and validates pool feasibility. Approved retest eligibility has no hard count cap; exposure limits may still make a safe form unavailable. No arbitrary 90-day exposure policy is silently inherited from an earlier proposal. Selection events/manifest are authoritative; materialized pool statistics are rebuildable. Random seed and full manifest remain staff-restricted, not candidate feedback.

## 6. Scoring, sessions, media and physical delivery

Objective scorer uses a closed format registry: single-choice/true-false exact match; multiple-select/matching/ordering explicit exact or declared bounded partial credit; blanks/bounded language tasks accepted variants with narrowly declared normalization. Reject unsupported or ambiguous scoring definitions at publication. Fixed decimal arithmetic, validated bounds and published rounding; no negative marking. Free/open language tasks, speaking and writing use human analytic rubrics. Criterion summaries do not become universal course cutoffs. Snapshot every scorer/key/policy version.

Server clocks govern section and overall candidate-work budgets. Store start/deadline and authorized pause segments; overall budget covers active work across sessions, not assessor marking or approved breaks. Background timeout sealing is a safety net: every read/write also checks deadlines. Retest eligibility, validity and appeal dates use approved event anchors and configured institutional timezone/working-day calendar. Protect retained component freshness and incident history; ordinary policies remain F03, not guessed section timing.

**Digital:** same-origin candidate delivery, typed writing and objective responses; live assessor-observed speaking or audio evidence. Current native non-Desk `upload_file` excludes audio MIME types (S4): do **not** widen core upload types or grant Desk to candidates. Use a purpose-specific owned authenticated upload command that writes native private File records after authorization and strict validation.

For recorded speaking select bounded **PCM WAV, 16-bit mono, with declared supported sample rates (16/44.1/48 kHz)**, using browser audio capture and standard-library WAV validation; no codec/transcoding dependency. Verify header/format/frame lengths, sample rate and duration, byte caps, purpose and attempt. Browser capture/playback support must be qualified. Periodic ordered upload segments carry sequence/hash and bounded size into private quarantine. Server-acknowledged segments are sealed at the capture deadline; finalization can assemble only already accepted content, never accept new speech after time expires. Missing/truncated tail is an incident, not a silently complete recording. Orphan/failed segments remain inaccessible and enter approved cleanup. Device failure offers the supervised live route; it cannot silently extend the recorded assessment.

**Physical:** controlled packet generated from the same allocated manifest; unique packet/script/page IDs, assigned invigilator, custody/return and actual start/end/incident evidence. Audio listening remains supervised. Staff transcription of objective answers is verified against the script before scoring; paper writing has rubric scores and custody evidence, with scans only if authorized. No claim that the server enforces physical time or prevents photocopying.

**Hybrid:** component mode is pinned before start; changes use incident authority and a new component/session revision. A paper score is never disguised as a digital response. Sampled/flagged unrecorded speaking needs a second live observer or documented follow-up. Preview/familiarization uses separate content and cannot allocate scored exposure unnoticed.

## 7. Server permissions and alternate native paths

Use native role permissions **plus** owned `has_permission` deny hooks, row filters and controller invariants. Hooks cannot grant absent native permissions (S2). Candidate data is served only by approved minimal projection commands; no read permission on full key-bearing/manifests/person documents is required.

Add an owned auth hook for placement-candidate profiles: allow only explicit login/session/logout, owned candidate-page resources and owned candidate commands after normalized path/method validation; deny generic CRUD, RPC/document methods, imports, report/export, native enrollment and other application commands. Reject conflicting candidate/staff/Student/Guardian profiles. Validate the effective dispatched callable as well as URL/method, including conflicting `cmd`/route parameters; a permitted page or asset URL cannot smuggle another callable. The exact route matrix must cover aliases/v1/v2 and dispatch names: unknown routes deny. Role users outside this profile retain their legitimate native work, not new placement privileges. Existing foundation guards remain active and unmodified.

Every owned controller checks immutable fields, transition context and actual authorizing actor independently of native mapping permissions. No generic submit/cancel/rename/delete/import for finalized placement aggregates. Block direct `db_set` changes to protected owned fields; audited exceptions use dedicated commands. Stock `db_set`/database writes bypass normal validation (S5): never claim hooks prevent arbitrary trusted Python/SQL. Restrict routine access to server scripts/system console/import administration; privileged operator actions remain audited and governed. No public generic setter or whitelisted document method may mutate protected state.

**Files:** add a deny-only File permission hook and a supported File class mixin in the owned app, composing `super()` with the unchanged foundation mixin. Guard `get_content`, `is_downloadable`, attachment creation/retargeting, privacy changes, deletion and domain-relevant mutations. Core File ownership/public/share exceptions and direct `get_content` are not adequate protection (S3/S4). Domain Files must remain private and bound to verified evidence/content ownership; account ownership alone never grants access.

Track protected canonical file identity/path and reject aliases, copies or retargeting that would expose the same protected bytes through another File record. Native list/report query restrictions must hide protected metadata as well as bytes. For candidates, custom media commands reauthorize active occurrence/evidence purpose and read in a narrow server-created context; generic private-file/ZIP/download endpoints remain denied. Staff downloads must pass both purpose/assignment checks and native File permission. Reject recursive File-parent authority and orphan domain files. Generic upload cannot attach to candidate evidence because candidates have no native parent write permission. Do not override all native upload behavior or relax its validation.

S1 confirms supported class-extension composition, not proven installed hook ordering. Runtime qualification of both mixins, native list/download/ZIP paths, aliases and revoke-after-upload is a hard acceptance requirement. Private-file URLs or browser hiding alone are not security boundaries.

## 8. Transactions, retry, history and retention

- Use native MariaDB transactions and explicit unique constraints. Operation receipt, invariant checks, business-state changes and dispatch intent commit together. Scope idempotency by operation/site and bind request hash, actor and subject. Same key/same authorized payload returns the existing result; changed payload or actor conflicts. Reauthorize retries; a revoked user cannot retrieve an old response through dedup.
- Canonical lock order: case → attempt/component → allocation guard → family exposure → relevant operation/result rows; each command takes only needed locks in this order. Atomic expected-revision updates reject stale autosaves/ratings. Serialize seal versus save, release versus revoke/hold and expiry/disposal versus legal hold. Deadlocks produce bounded whole-command retry using the original key, not partial resubmission.
- Native `enqueue_after_commit` is a callback, not a durable outbox (S6/S7). Persist dispatch intent in Operation; after-commit enqueue reduces latency and a reconciler redelivers pending work after crashes. Workers reauthorize/recheck scope and current policy/hold, deduplicate by operation/result version, and never assume exactly-once execution. Queue loss cannot lose the committed assessment.
- Filesystem writes are not database-atomic: stage private media, commit evidence references only to verified sealed content, reconcile orphan/absent files after rollback/crash. Never mark a partial upload complete. Retention uses durable hold-checked disposal intents and exclusive per-evidence coordination; holds cannot resurrect already lawfully deleted bytes. Preserve disposal audit and explicitly report diminished re-marking ability.
- F05 durations and event anchors are approved; jurisdiction, notices/holds, actual population and backup-expiry mapping are required activation config. Restoration into isolation must reapply revocation/deletion/holds before serving data. Retain policy/form references needed for retained summaries; no restored backup may silently restart retention. Reporting uses separate placement grains and rebuildable projections, never an editable score master.
- Install/migrate only owned records and reviewed indexes after authorization. Start with domain operations disabled. No migration changes native required fields or rewrites historic Student/finance data. Roll back owned code only to a schema-compatible version; restore/reconcile in isolation when necessary. Do not uninstall by cascading deletion of retained placement evidence.

## 9. Configuration-later boundary

Published, versioned **operational policy profiles** bind actual course mappings, age-appropriate content, quotas/time/navigation, rubric rules, exposure policy, accommodations, identity/delegation, working-day calendar and lawful data-use/retention procedures. Draft/missing/incompatible config disables allocation, evidence collection, recommendation or release as applicable. No approved F01–F05 value is reopened; profiles cannot restore withdrawn 70%/16+/hard-attempt-cap defaults.

An authorized isolated build may use visibly synthetic subjects, curriculum, keys and policies with a non-operational marker. No production seed, real learner recording or real credentials; the marker cannot be removed by copying a fixture. Owner artifacts remain required before activating the corresponding real workflow, not before writing parameterized code. Actual assessment validity trials and real-data operation need separate authorization and governance. Runtime policy validation and denial of incomplete configuration are acceptance tests, not documentation promises.

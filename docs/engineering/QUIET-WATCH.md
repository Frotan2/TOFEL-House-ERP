# Quiet-period / no-silent-change watch

## What it is

A sha256 lock (`quiet-watch-lock.json`, maintained by
`tools/foundation/quiet_watch.py`) over the small set of files whose silent
change would corrupt a release verdict. The owned suite
(`tests/foundation/test_quiet_watch.py`) fails on any mismatch, so a quiet
edit turns CI red instead of rewriting history.

## Truly-current state vs docs (verification basis, 2026-09-19)

The lock was sealed on content verified live on 2026-09-19, not on stale
claims: Frappe/ERPNext/Education/HRMS release tags and branch-head SHAs
re-fetched from GitHub, PyPI latest versions re-queried (pdfkit 1.0.0,
pypdf 6.19.0, setuptools 84.0.0, WeasyPrint 70.0), both GHSA advisories
without patches re-read, HRMS manifests confirmed byte-identical, and the
Python reachability of all 7 findings traced at pinned Frappe v16.33.1
(`evidence/sec-deps-01/pdf-reachability-trace-2026-09-19.md`). The locked
baseline therefore describes the true current upstream state as of the seal
date; any upstream movement after it is a NEW event to assess, never a
silent invalidation of these records.

## Allowed deliberate change

A locked file changes **only** in a commit that, in the SAME commit:

1. Edits the file with a real, reviewable diff (no unexplained rewrites);
2. Regenerates the lock (`python3 tools/foundation/quiet_watch.py`);
3. Carries a commit message stating what changed and why.

Additionally: `foundation-version-matrix.json` changes require a
re-qualification note (what was re-verified against the new pins);
dated assessment files must never be edited in place — a new dated
assessment supersedes them.

## Drift alarm

Anything else: the suite fails with `DRIFT: <path> differs from the
quiet-watch lock`. The response is investigation, never blind lock
regeneration. Regenerating the lock without a reviewed file diff is itself
a silent change and is forbidden.

## Deliberately NOT locked (with reasons)

- **Append-only ledgers** (`execution-ledger.json`, …): legitimate runs
  append; locking would cry wolf on every real execution.
- **Per-run outputs** (`foundation-test-results.json`, `hosted-*.json`):
  regenerated by running things; freshness is their nature.
- **Living owner records** (`canonical-owner-decision-record.json`,
  `OWNER-DECISIONS.md`): owned by the owner-decision process, which is the
  review ceremony for those files.
- **Living tracking docs** (`UPSTREAM-TRACKING.md`, …): updated by
  inspection rounds; each round is its own dated, reviewable commit.
- **Generated projections** (`FINAL-CLOSURE-REGISTER.md`, …): guarded by
  their own freshness tests against their JSON sources.
- **App code and fixtures**: change constantly during implementation; the
  owned suite, fixture tests and permission guards are the watch there. A
  hash lock would be pure noise.
